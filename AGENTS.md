# AGENTS.md

Monorepo toolchain for VK Mini Apps. pnpm workspaces, TypeScript strict, ESM-only.

## Structure

- `packages/bridge`, `packages/deploy`, `packages/devtools`, `packages/api-schema` — publishable libraries (tsdown: ESM + dts)
- `packages/router` — TanStack-based VK Mini Apps router (v0.1 implemented, pre-release; `DESIGN.md` is the source of truth for decisions, read its `AGENTS.md` before touching)
- `packages/bridge-schema` — JSON Schema catalogue of VK Bridge events + generated types
- `packages/api-schema` — generated TS types + zod/valibot schemas for the VK API, built at build time from the `VKCOM/vk-api-schema` git submodule
- `packages/protocol` — private: wire types (`WireEvent`, `ClientInfo`, …), the client palette, zod trust-boundary schemas and `RELAY_CHANNEL`; consumed (and inlined) by devtools, ui and the extension
- `packages/ui` — private, source-only: design tokens (Tailwind v4 CSS-first `styles.css`) + the presentational devtools panel components; data layers live with consumers
- `apps/web` — docs & demos site (bare Astro, no React yet)
- `apps/devtools-extension` — browser extension (rsbuild + React, MV3 chrome-first + firefox manifests, `web-ext` to run/pack): the vkma.dev panel on arbitrary vk.ru pages, direct-connect or spy mode (see its section below)
- `apps/inspect` — remote inspector (rsbuild two-pass): the panel at `/` + the single-file `/inspector.js?id=<peer id>` pasted into mini app pages (phone webviews, prod builds, third-party apps); PeerJS signaling + WebRTC data, no dev server, no extension (see its section below)
- `playground/mini-app` (Vite) and `playground/mini-app-rsbuild` (Rsbuild) — fake mini apps for manual e2e of the devtools adapters (import the original `@vkontakte/vk-bridge` so the plugin's interception is what routes it through the tap; `VKMA_MCP=1` enables the MCP route)

## Bridge packages (`packages/bridge`, `packages/bridge-schema`)

`@vkma.dev/bridge` is an independent VK Bridge (no `@vkontakte/vk-bridge` dependency); `@vkma.dev/bridge-schema` owns the event catalogue. The non-obvious invariants:

- **The catalogue is data, extracted once**: `bridge-schema/schema/events.json` is checked in and hand-maintained. `pnpm --filter @vkma.dev/bridge-schema bootstrap` re-extracts it from the reference devDependency (`@vkontakte/vk-bridge`, catalog-pinned) via the TS7 unstable sync checker; that script is the only place allowed to touch the JSON. Sync ritual: VKCOM publishes a release → bump the catalog version → bootstrap → review the JSON diff → the parity tests tell you if the types drifted. There is no automation watching upstream — subscription to VKCOM releases is manual.
- **Augmentation lives in the schema package ROOT**: the three catalogue maps (`RequestPropsMap` / `ReceiveDataMap` / `ReceiveEventMap`) are emitted as `interface`s in `src/index.ts` (generated) on purpose — `declare module` merging only works against the declaring module, so consumers extend the catalogue by augmenting `@vkma.dev/bridge-schema`, never `@vkma.dev/bridge`. Interface merging is extend-only; fixing VK's own payload types means a new schema version, never an override.
- **Map entries reference `$defs` by name; json2code is the only TS printer**: the bootstrap writes pure JSON Schema (a subset json2code understands), generate.ts never prints payload types by hand. Divergences from upstream type expressions (intersection merging, `any`→`unknown`, `object`→`{}`, generic aliases degraded to `unknown`) are documented in the bootstrap header.
- **The tap is core, not a wrapper**: every bridge instance carries a replay-buffered tap; `onSend`/`onEvent` sit on the instance, `send` pairs responses via the injected `__vkma_<n>` request_id (policy in `VkmaBridgeOptions`). The tap payload must never be mutated after emit — send builds a separate wire-props object for exactly this reason.
- **Wire parity over convenience**: the `vk-connect` envelope, the four transports (web postMessage, Android, iOS, RN), `VKWebAppSettings` frame-id assignment and the `SetSupportedHandlers` caching reproduce the platform contract the host clients implement. `parent.postMessage` uses `"*"` because the host origin is unknowable ahead of time — do not "fix" that.
- **Transports read the host lazily** (per call), unlike upstream's import-time caches — that's what makes the happy-dom unit tests possible. Mobile WebView transports are contract-tested via fakes only; run the manual device checklist before a release.
- **Devtools dependency direction**: `devtools` never imports the bridge at runtime — the inject collector talks to `globalThis.__vkmaDevtoolsBridge` through structurally declared local types. The resolveId skip for `TAP_IMPORTERS` stays even though the clone no longer imports the original: installed older wrapper versions (peer `>=0.0.0`) still do.

## API schema (`packages/api-schema`)

`@vkma.dev/api-schema` is fully generated — read `packages/api-schema/AGENTS.md` before touching the generator. Root-level invariants:

- **Generated code is never committed**: `src/generated/` and `.schema-transformed/` are build intermediates; build/test/lint all generate first. Typechecking the package on a fresh clone without a generate pass fails by design — run `pnpm generate`.
- **The version minor is the API version**: `0.5199.x` ↔ API `5.199`; the generated `API_VERSION` is asserted by a test. Schema updates go through `pnpm update-schema` (bumps the submodule to upstream master + regenerates) and ship via changesets with the minor realigned.

## Devtools architecture (`packages/devtools`)

Read `packages/devtools/PRODUCT.md` for product truth and `DESIGN.md` for the visual system. The non-obvious invariants:

- **Single source of truth**: events live in the node side's ring buffer (500) and flow to every surface over devframe RPC. The FAB iframe and the standalone `/__vkma/` tab render the same data; do not add client-side-only event paths.
- **The tap is on `globalThis`**: `@vkma.dev/bridge` publishes `{ tap, send }` as `globalThis.__vkmaDevtoolsBridge`. The inject collector finds it there — it never shares a module graph with the app. The tap's buffer (500) replays to the first subscriber, so the collector may attach after the app started sending.
- **Interception is a resolveId hook, not an alias**: the vite plugin redirects `@vkontakte/vk-bridge` imports via an `enforce: "pre"` `resolveId` that must SKIP importers inside `@vkma.dev/bridge` itself — otherwise a redirect target importing the original turns the "alias" into a self-cycle (TDZ crash). Do not replace this with `resolve.alias`.
- **Two bundler adapters, one contract**: the rsbuild adapter (`@vkma.dev/devtools/rsbuild`, `vkmaDevtoolsRsbuild`) mounts the same panel/RPC/collector as the vite plugin. rspack's `resolve.alias` is importer-agnostic (it would loop the tap onto itself), so interception there is `NormalModuleReplacementPlugin` applying the same `TAP_IMPORTERS` skip; `alias: false` turns the rewrite off in both adapters (apps importing `@vkma.dev/bridge` directly). Rsbuild's connect stack never hands over HTTP upgrades, so the RPC socket is a side-car WS server on its own port, discovered via `<base>__connection.json`; the devframe instance rides on `globalThis` to survive dev-server restarts. `playground/mini-app-rsbuild` is its manual e2e target.
- **The MCP route is opt-in and layered**: the `mcp` option (both adapters) exposes agent tools at `<base>__mcp` (stateless Streamable-HTTP) — default off. `mcp: true` is the origin-only default: requests WITHOUT an `Origin` header get 403 (anti-DNS-rebinding, so non-browser MCP clients must send one) and the connected peer must be loopback; `allowedOrigins: false` lifts both, a bearer-token `McpSetting` hardens tunnels/LAN and lifts the loopback restriction for authenticated callers. Separately, the app PAGE's RPC (WS) sits behind devframe's interactive OTP gate on first connect (code in the dev-server terminal / `#devframe_otp=` link; trusted browsers remember) — an unauthenticated page never registers a client. The bridge's reserved `__mcp`/`__sse` routes must never be eaten by a SPA fallback — that bug once served the panel at `/__vkma/__mcp` instead of the MCP stream.
- **MCP tool shapes**: agent-flagged RPC functions project their declared args positionally (`arg0`, `arg1`…) — a single-payload RPC arg surfaces as `{ arg0: … }` on the wire and flat input dies with DF0043. Single-payload agent tools are plain `ctx.agent.registerTool` registrations with an explicit flat `inputSchema` (the override wins; the handler receives the caller's input as-is) — `vkma:mcp-execute` is the reference.
- **Inject loading order**: the plugin injects a plain (non-module) script that sets `globalThis.__VKMA_DEVTOOLS_BASE__` and appends the module tag at runtime. Deriving the base from `import.meta.url` breaks when a dev pipeline inlines the module as a data: URL; letting Vite rewrite a module `src` in index.html breaks too. The collector waits for the bridge handle (`waitForBridge`) because dynamic module insertion races the app's graph.
- **Mount order**: the static SPA mount comes BEFORE `devframeViteBridge` — the bridge's router is terminal and would 404 the panel files. The plugin's `configureServer` also 308-redirects `/__vkma` (no slash) to `/__vkma/` — relative asset URLs in the panel HTML resolve against the parent directory otherwise — and chains `server.printUrls` (unocss-style) to print the panel URL on `pnpm dev`.
- **Sessions**: the collector sends a per-page-load `sessionId` in `vkma:hello`; when the node side sees a new session for a known client it purges that client's history and broadcasts `vkma:on-session-reset`. Client ids persist across reloads (sessionStorage), session ids do not. `connectedAt` is first-seen per session — the store pins it against heartbeat re-stamps — and anchors the registry order and the "connected N ago" label.
- **Duplicate tabs yield their copied client id**: "Duplicate Tab" copies sessionStorage, so two live tabs could share one clientId — interleaved traffic in a single card and its history wiped every heartbeat (alternating sessionIds). The inject runs a BroadcastChannel claim handshake on `vkma:client-ids`: an incumbent answers `taken`, the claiming tab mints a fresh id; claims are re-asserted every 30s so a duplicate whose twin was timer-frozen also settles. A plain reload (sole holder) keeps its id.
- **Clients never vanish on a timer**: Chrome throttles background-tab timers, so heartbeat-based deletion would flap clients offline/online. Past the 15s heartbeat TTL a client is marked `online: false` (dimmed card, "offline" chip) and only the registry cap ever drops entries — enforced AT INSERT (the oldest offline entry makes room for a newcomer; if every slot is online the newcomer is refused, so one connection minting fresh ids cannot grow the registry past 24). The inject says hello immediately on `visibilitychange` so a refocused tab comes back online instantly.
- **Embedded mode**: the FAB appends `?client=<id>` to the panel iframe; `useVkma(clientId)` then scopes state/events/execute to that client and hides the Clients tab and target selector.
- **Embedded panels are scoped on the node, not in the panel**: the `?client=` session calls `vkma:subscribe { clientId }` right after connect, and the node then delivers only that client's events/registry/resets via targeted broadcasts (filter identity: `client.$meta === session.meta`) plus a scoped `vkma:state` snapshot. `/__vkma` standalone keeps the full feed. The panel's local filters are a race net, not the mechanism; `vkma:execute` rejects cross-scope targets with the `forbidden` ExecResult. Standalone `/__vkma/` shows everything plus a per-client switcher in the filter row.
- **Client colors are deterministic**: djb2 hash over a curated 8-tone palette in `src/shared/colors.ts` (raw hex — the FAB's shadow DOM paints its outlined glyph's stroke with it; the FAB re-paints when a duplicated tab yields its copied id). The panel maps indexes to Tailwind classes in `app/src/lib/colors.ts`. Same client → same color everywhere (timeline badges, client cards, header badge, FAB glyph stroke). Never derive them from registry order or random values.
- **Event dedupe**: delivered events are merged by `seq` (globally unique, assigned by the node side) in `useVkma` — closes the snapshot+subscribe race and double deliveries. `data-seq` on timeline rows is the e2e assertion hook.
- **`vk-connect` is transport chatter**: the collector drops it before reporting; don't surface internal bridge protocol events in the timeline.
- **Sensitive params** (`sign`, `access_token`, `auth_key`, `sid`) are blurred in the Clients launch-params grid — the grid lives in `@vkma.dev/ui` (`Clients.tsx`) and is shared with the extension; keep the set in one place.
- **Wire names** live in `src/shared/protocol.ts` (`VKMA_RPC` + the `DevframeRpcClientFunctions` augmentation). Browser-registered functions must be declared there or broadcasts/registers stop type-checking. The wire TYPES themselves live in `@vkma.dev/protocol` (inlined into the published dist via tsdown `deps.alwaysBundle` — the package is private, so devtools must never import it at runtime from dist); the extension imports the built package.
- **SPA builds**: `pnpm build` in the package = SPA (`app/` → `dist-client/`, base `./`) → inject bundle (`vite.inject.config.ts` → `dist-client/inject.js`, don't flip `emptyOutDir`) → tsdown lib. `dist-client` ships in the npm package and is git-ignored. Always run the full `pnpm build` in the package — a lone `build:client` wipes `dist-client` (including `inject.js`) before re-adding it.
- **JsonTree** (`app/src/components/JsonTree.tsx` + `JsonTree.module.css`): hand-rolled collapsible viewer (devframe ships none; json-render is a UI spec). CSS modules + light/dark token sets; nodes are memoized. NOTE: the presentational components (JsonTree included) physically live in `@vkma.dev/ui` since the extension extraction — `app/src` keeps only the data layer (`useVkma`), `StatusGate` and the entry.

## Devtools extension (`apps/devtools-extension`)

The extension runs the same panel on pages the dev-server plugin can never touch (prod builds, third-party mini apps). The non-obvious invariants:

- **Two capture modes, one signal**: `globalThis.__vkmaDevtoolsBridge` present in the page world → **direct** (the app runs `@vkma.dev/bridge`); absent → **spy**. The MAIN-world relay (`relay.js`, dependency-free, ~0.7 kB) polls the handle and mirrors the tap to the isolated world over the reserved `__vkmaExt` window channel — the react-devtools pattern, zero changes to the bridge package. A page script can fake relay messages, but it could emit that traffic itself anyway — no extension privilege is exposed; the same reasoning covers the sniffer.
- **Spy mode is two half-listeners**: host→app traffic is seen by a second `@vkma.dev/bridge` instance living in the frame's ISOLATED world (window `message` fires in every world — the vk-mini-app-spy trick); app→host requests are sniffed in the TOP frame (`type === "vk-connect"` postMessages). They are joined by the wire `request_id`: sniffed sends get store-local ids, incoming tap "events" carrying a pending id are reclassified as `response`s. Direct mode ignores the sniffer entirely (the tap is authoritative — no doubles); the collector's own executes carry the reserved `__vkma_ext_` request-id prefix so the sniffer drops them.
- **Envelope attribution**: sniffed envelopes map to clients by `webFrameId` (captured raw from `VKWebAppSettings`, which the bridge swallows) with `event.origin` fallback; unattributable frames (ads, service iframes) are dropped — that filter is what fixes the spy's cross-talk weakness.
- **The host script is the node side**: the top-frame content script of VK hosts runs the very same `DevtoolsStore` (imported from `@vkma.dev/devtools/store` — a subpath export precisely because the main entry drags vite/devframe) plus the `vkma` werpc namespace: `state`/`timeline`/`clientsChanged`/`sessionReset` for panels, `hello`/`push`/`execResult`/`executeRequests` for collectors, `execute` (timeout-guarded by the store). Contexts glue over werpc (`scopeToTab` + `fanout`); the SW is only the router + the side-panel state machine (`sidePanel.open()` needs a gesture, which only survives raw one-shot runtime messages — hence `OPEN_SIDE_PANEL_MESSAGE`).
- **History is per page load**: the store dies with the host page (no dev server to outlive reloads). Client ids are minted fresh per collector init — persisting them would collide between same-origin sibling frames sharing the tab's sessionStorage.
- **One panel page, three surfaces**: `panel.html?view=all` (the action icon) is the wide surface — every VK tab at once, one werpc client per host tab merged by `MergedTimeline` (host seqs collide across tabs; the merger derives a stable global seq per (clientId, hostSeq) and orders by wire ts) — the /__vkma/ standalone panel's counterpart; the FAB iframe (`?tab=<id>`, mounted by the host script, hidden while the side panel is open) and the side panel (no query, resolves its tab via `tabs.query`, the spy's pattern) stay tab-scoped. The connection adapters mirror `useVkma`'s contract: seq-deduped timeline, short probe timeout so a host-less tab fails fast, no OTP (extension messaging is trusted). Offline clients are removable from the Clients tab — live ones are skipped server-side (a running collector re-registers within a heartbeat). Firefox has no sidePanel — the background guards on it and the manifest omits it.
- **Host list**: top frames match the curated VK host list (`*.vk.com`/`*.vk.ru` cover `m.`/`cs7777.`/`tau.` subdomains; plus vk.me, dzen, ok/okcdn, gameroom, vkvideo, max); frame/relay scripts match every http(s) frame and self-identify as mini apps at runtime (`framed` + `sign`/`vk_app_id`/`vk_platform`). Standalone mini apps (top-level, no host) are a deliberate v1 gap.
- **Trust boundaries are zod-parsed** (`@vkma.dev/protocol/schemas`): sniffer envelopes, relay messages and werpc inputs — invalid input drops silently, like the collector drops `vk-connect` chatter. `RELAY_CHANNEL` lives in the zod-free package root so the relay stays dependency-free.

## Remote inspector (`apps/inspect`)

The inspector reaches pages the other two surfaces never can: the VK webview on a phone, prod builds, third-party apps. The non-obvious invariants:

- **Two passes, one dist**: `pnpm build` runs the panel SPA first, then the inspector pass (`cleanDistPath: false`) — `dist/inspector.js` must stay ONE self-contained file with zero ESM-only syntax (no `import.meta`, no `import`/`export`): the same bytes run as a classic `<script>` in a foreign `<head>` and as a console `import()` (CORS comes from `public/_headers`). `src/inspector/artifact.test.ts` enforces it post-build. Never merge the entries into one build — shared chunks break the single-file contract.
- **Hooks in before the app's bridge imports**: vk-bridge freezes `window.AndroidBridge` / `webkit.messageHandlers` refs at import, so the native wraps install in the `InspectorCapture` constructor (first thing `main()` does) at TWO visibility levels — in-place method mutation (seen by already-captured refs, the console-import case) and a window-level Proxy (fresh readers + handlers the native side adds later). Always forward-then-tap: the page must behave as if the inspector were never there.
- **Mode resolution buffers**: captured rows buffer until the `__vkmaDevtoolsBridge` question settles (10 s). The global is page-writable and first-writer-wins, so presence proves nothing — `waitForBridge` adopts only a handle SHAPED like a genuine bridge tap (subscribe/emit/drain, drain returning rows), and adoption never mutes the head-first raw layers: direct mode sinks the tap's OUT rows only (its replay merged with the spy-era buffer, deduped by wire `request_id`), while the raw listeners own the incoming direction in EVERY mode — a page-planted handle can add rows but cannot blind the independent capture. Executes ride the inspector's private bridge instance in every mode (the adopted handle's `send` is page JS of unverified provenance).
- **The `__vkma_inspect_` request-id prefix** names the collector's private `@vkma.dev/bridge` instance — but the raw layers' skip license is ISSUER-SCOPED and one-shot (a Set of ids the instance actually issued, consumed on first use), because the prefix itself is public in `/inspector.js`: a page tagging its own sends with it must not elide them. The instance's tap contributes the `send` rows in every mode. Pairing needs no bridge instance at all: vk-bridge injects `request_id` into params BEFORE the transport fires, so intercepted sends join raw responses through the `RequestJoiner`.
- **The wire protocol is six JSON messages** over a PeerJS DataChannel (`hello`/`events`/`exec-result`/`challenge` up, `execute`/`challenge-proof` down, `v: 1`) — deliberately NOT werpc: werpc's only transport is `chrome.runtime.Port`, faking that global inside someone else's page risks extension-detection breakage. Payload types and zod schemas come from `@vkma.dev/protocol`; the host zod-parses everything crossing a connection and drops invalid input silently.
- **Dial-direction trust (challenge-response)**: the inspector ships credentials ONLY after the answering peer signs a fresh nonce with the panel's ECDSA key — the peer id proves nothing (the broker re-grants a stopped id to whoever registers it first, verified against the public cloud). The private key lives in the panel origin's localStorage; the snippet embeds the public half (`&k=`). The host answers `challenge` BEFORE gate admission (the proof discloses nothing, and without it no hello — hence no approval card — would ever arrive); `DialTrust` (inspector) queues every credential until verification and drops the connection on a bad proof. A stale snippet without `k=` sends nothing at all.
- **Panel and store share one process**: `useInspect` subscribes to the host's hubs directly (no RPC — the extension needed werpc only because its panel and host live in different contexts). The runtime is created ONCE at module scope in `main.tsx` so StrictMode remounts don't kill the peer.
- **The approve gate is ON by default** — a leaked peer id grants `vkma:state` with launch params. Admission is a property of the CONNECTION: an undecided connection parks EVERY message type (bounded by count AND bytes), so a peer that never says hello — and therefore never faces an approval card — cannot reach the store at all; "allow once" sets `admitted` for that connection (heartbeats flow, a fresh connection re-parks); "always" persists the clientId. Wire identity is frozen per connection (one connection, one clientId; a duplicate claim of a live id is closed, never silently re-bound), exec-results settle only on the connection the execute was routed to, and `deny` revokes a persisted "always" grant (it must survive reloads exactly like the grant does) AND disconnects an already admitted connection — a trusted-then-hostile page stops streaming without a panel reload. Rotate clears the approved list — trust re-anchors to the fresh capability.
- **Peer id lifecycle**: sessionStorage holds this tab's id (survives reloads — the phone's snippet keeps pointing at it) and the id is SESSION-LOCAL by default: localStorage holds it only when PINNED (explicit opt-in in the setup sheet — snippet stability across tabs). The broker hands a stopped id to whoever registers it first (verified against the public cloud: re-grant lands within ~300 ms of the holder dying, the registration token proves nothing), so an unpinned leaked id dies with its tab. A BroadcastChannel claim handshake settles duplicates before the Peer is created; Rotate re-pins the replacement so a burned id never revives from the pin. `unavailable-id` retries once, then surfaces Rotate.
- **STUN-only, no TURN, ever**: `ICE_SERVERS` in `src/shared/config.ts` is the whole policy — relays are architecturally absent, an unpierceable pair fails honestly (LTE↔symmetric-NAT is a documented miss). Signaling is the public PeerJS cloud; a self-hosted broker is a one-line switch in the same file.
- **Deployment**: Cloudflare Workers static assets (`wrangler.jsonc`, SPA fallback) — `/` and `/inspector.js` are plain files; the app stays private, no changesets.

## Commands (root)

- `pnpm build` / `pnpm dev` — recursive over all workspaces
- `pnpm lint` — oxlint + `tsc -b --noEmit` + apps typecheck + `pt format --check` + publint (run `pnpm build` first: publint needs `dist/`; lint generates `src/generated` for both schema packages first — a fresh clone has no generated code to typecheck until then)
- `pnpm test` — vitest per package
- `pnpm update-schema` — bump the `vk-api-schema` submodule to upstream master + regenerate `packages/api-schema`
- `pnpm format` — oxfmt via `pt format`

## Conventions

- Shared dependency versions live in the `catalog:` section of `pnpm-workspace.yaml`.
- Publishing: changesets (`pnpm changeset`, `pnpm version`). Apps stay private.
- Changeset summaries stay one short line — the details belong in the commit message, not the changelog.
- Extension browser target: `BROWSER=firefox|chrome` (default chrome), two static manifests in `apps/devtools-extension/src/`, `web-ext` to run/pack (`pnpm start` / `pnpm build:chrome` in the app).
- Node >= 22.18 (type stripping for generator scripts), dev machine version pinned in `.node-version`.
